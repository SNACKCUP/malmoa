# 2026-11-03 저장소 분리 (STORAGE_BACKEND=local | s3)

브랜치 `feat/llm-settings` (커밋 전). 배포 계획 "로컬 파일 저장" 항목 (`2026-11-03-배포목표와결정사항.md` 1장).

## 요청

"업로드 원본·변환 원문·회의록을 로컬 폴더 대신 설정으로 S3 호환 저장소에도 저장할 수 있게. 기본값 local(지금 동작 유지). meerkit의 app/storage(공개/비공개 버킷 분리)를 참고하되 회의 녹음은 반드시 비공개 버킷. 기존 파일을 옮기는 스크립트는 따로, 실행은 승인 후. 완료 기준: local 모드 기존 테스트 통과, s3 모드는 로컬 Supabase/MinIO로 시험."

추가 조건 (사용자): 테스트 준비 단계 쓰기도 저장소로, work_dir 줄은 그대로, 예전 이름→`moa-` 테스트는 local 전용, 실제 경로·키 확인 테스트 추가, s3 테스트는 `.env`의 저장소 값을 절대 쓰지 않기, local 경로 테스트는 임시 폴더, s3 모드에서 로컬 폴더에 파일이 안 생기는지·다른 작업 파일이 안 지워지는지 테스트, 이전 스크립트는 만들기까지만(실행은 미리보기 → 백업 → 승인, 로컬 파일 안 지움).

## 구조

```
services/file_store.py
  키: uploads/<작업ID>.<확장자> · transcripts/<작업ID>.json|.txt · minutes/<작업ID>.json|.md  (원래 파일 이름 없음)
  FileStore 모양: put_bytes · put_file(큰 파일, 올린 뒤 원래 파일 없어짐) · get_bytes · exists · delete · list(접두사)
                  · local_copy(진짜 파일이 필요할 때 잠깐 꺼내기) · iter_bytes(다운로드 응답) · check(시작 확인)
  LocalStore  backend/storage/<key> — 예전과 같은 폴더 배치. 저장소 밖을 가리키는 키(../ 등)는 거부
  S3Store     비공개 버킷 하나 (STORAGE_PRIVATE_BUCKET). path 방식 주소(Supabase), 16MB 넘으면 분할 업로드
```

- **비공개 버킷만**: meerkit은 공개(`STORAGE_BUCKET`)·비공개(`STORAGE_PRIVATE_BUCKET`)를 나누지만, 말모아 파일은 녹음·원문·회의록이라 모두 비공개 하나에 둔다. 공개 주소·미리 서명된 주소를 만들지 않고, 파일은 로그인 확인 뒤 백엔드가 전달한다(`/file`은 조금씩 읽어 보내는 StreamingResponse). 객체에는 `Cache-Control: private, no-store`.
- **work/ 는 항상 로컬**: ffmpeg·Whisper는 진짜 파일이 필요하고, 구간 저장·이어서 하기는 변환하는 컴퓨터 안에서만 의미가 있다. S3 모드에서는 원본을 `work/`에 잠깐 내려받아(`local_copy`) 변환하고 끝나면 지운다.
- **업로드**: 예전처럼 1MB씩 받으며 크기 제한을 확인하되, `work/incoming/`에 받은 뒤 저장소로 옮긴다(local은 이동, S3는 업로드). 실패·거부 때 임시 파일은 지운다.
- **설정** (meerkit과 같은 이름): `STORAGE_BACKEND`(`local`|`s3`, 기본 `local`), `STORAGE_PRIVATE_BUCKET`, `STORAGE_S3_ENDPOINT_URL`, `STORAGE_S3_REGION`, `STORAGE_S3_ACCESS_KEY_ID`, `STORAGE_S3_SECRET_ACCESS_KEY`. `s3`인데 값이 비었거나 버킷에 닿지 못하면 서버가 시작하지 않고 이유를 알린다.
- **local 모드는 예전 그대로**: 시작할 때 `uploads/·jobs/·transcripts/·minutes/` 폴더를 만든다(처음 고친 판에서 이 줄이 빠져 테스트 2개가 실패 → 되돌림). DB 도입 전 JSON 작업 옮기기(`jobs/`)는 local 모드에서만.
- **삭제 범위**(같음): 저장소의 원본 + `transcripts/<작업ID>.*` + `minutes/<작업ID>.*`, 로컬의 `work/<작업ID>`·`work/<작업ID>_minutes`·`jobs_legacy/<작업ID>.json`.
- 라이브러리: `boto3`(meerkit과 같음), 개발 전용 `moto[server]`.

## 로컬 Supabase 실제 확인

meerkit 개발용 로컬 Supabase(`supabase_storage_meerkit`)에 시험 버킷 `malmoa-check-private`를 따로 만들어 확인하고 지웠다. S3 키는 확인 스크립트의 환경변수로만 넘겼다(`.env`에 쓰지 않음).

1. 시작 확인(head_bucket) 통과
2. 원본(한국어 회의 녹음) 업로드 → 임시 파일 정리
3. 진짜 Whisper small 변환 → 버킷에 `transcripts/….json·.txt`, 원문 4문장 정확
4. 로컬 storage 폴더에 남은 파일 없음
5. 로그인 없이 공개 주소·객체 주소로 열기 → 둘 다 HTTP 400("Bucket not found" — Supabase는 비공개 버킷을 이렇게 숨긴다. 같은 시점에 S3 API로는 읽혔으므로 버킷은 있었음)
6. 20MB 파일 올리기·내려받기 → 내용 같음. Supabase는 ETag에 조각 수(`-2`)를 붙이지 않아 **실제로 나눠 올렸는지는 확인하지 못했다** (분할 업로드는 moto 40MB 테스트로 확인)
7. 삭제 → 버킷 비움 → 버킷 삭제

**알게 된 것:** 로컬 Supabase Storage는 파일당 **50MB 제한**(`FILE_SIZE_LIMIT=52428800`). 2시간 녹음은 넘을 수 있다 → 배포 저장소를 고를 때 파일 크기 한도를 꼭 확인 (배포 결정 문서에 메모). MinIO 이미지는 Docker Hub(접근 거부)·quay.io(없음)에서 받을 수 없어 쓰지 않았다.

## 기존 파일 이전 스크립트 — 만들기만, 실행 안 함

`backend/scripts/storage_migrate.py`

1. `preview` (기본): 올릴 파일 수·크기, 이미 버킷에 있는 것. 버킷은 읽기만
2. `backup`: `storage/uploads·transcripts·minutes` 사본 + 파일별 SHA-256 목록(`manifest.json`) + DB 덤프를 `../backups/`에 (권한 600)
3. `apply --backup <폴더>`: 백업이 있고 지금 파일과 같아야 시작 → 파일마다 올린 뒤 내려받아 SHA-256 비교 → 결과를 백업 폴더에 기록. 같은 것은 건너뜀. **로컬 파일은 지우거나 바꾸지 않는다** (올릴 때도 사본을 올림)

옮기는 것은 `uploads/·transcripts/·minutes/`뿐 (`work/`, `jobs/`·`jobs_legacy/`, `postgres/`, 쓰다 만 `.tmp`는 제외). 대상 버킷은 `.env`의 `STORAGE_PRIVATE_BUCKET`·`STORAGE_S3_*` (`STORAGE_BACKEND` 값은 보지 않음 — 옮기고 확인한 뒤 사용자가 `s3`로 바꾼다). 가짜 파일로만 시험했다.

**실제 백업 실행 (2026-11-03 15:12, 사용자 요청 "백업 해줘")** — `apply`는 실행하지 않음, 버킷에는 접속하지 않음.

- `preview`: 파일 62개 — uploads 18개(532,450,158 B), transcripts 36개(3,905,308 B), minutes 8개(36,975 B)
- `backup` 결과: `backups/storage-20261103-151211/` (512MB, `manifest.json`에 파일별 크기·SHA-256) + `backups/malmoa-db-before-storage-migrate-20261103-151211.dump`
- 확인: 스크립트는 SHA-256을 **원본**에서 계산하므로 사본을 따로 다시 계산해 비교 → 62개 모두 일치. 덤프는 `pg_restore --list`로 열어 표 10개(users, jobs, people, events, event_reminders, llm_settings, llm_usage, llm_usage_limits, recorder_beats, alembic_version)의 데이터가 들어 있음을 확인
- 권한: 파일 600, 스크립트가 만든 폴더가 755여서 700으로 좁힘 (스크립트 자체는 고치지 않음 — 폴더 권한도 700으로 만들게 고칠지 결정 필요)
- 백업은 원본과 같은 디스크에 있다. 통합·배포 같은 큰 작업 전에는 외장 디스크·클라우드에 한 벌 더 둘 것
- 말모아가 켜져 있는 동안(자동 녹음 포함) 복사했다. 그 사이 새로 생긴 파일은 이 백업에 없다

## 확인하지 못한 것
