## 한 줄 결론

**로그인·토큰 처리(킷)는 두 서비스가 완전히 같다.** 다른 것은 킷 *위에서* "누가 서비스를 쓸 수 있나"를 정하는 방식과, 서비스마다 따로 만든 토큰(말모아: Mac 작업자 열쇠·캘린더 구독 주소 / 매무새: 프로젝트 초대 링크)이다.

## 1. 같은 것 — 킷(meerkit 0.1.0-rc.10)

| 확인 | 결과 |
|---|---|
| meerkit 버전 | 둘 다 `0.1.0-rc.10` (`.meerkit/manifest.json`) |
| 백엔드 킷 폴더 `auth`·`core`·`users`·`account`·`permissions`·`social`·`codes`·`mail` | **두 프로젝트 파일이 한 글자도 다르지 않음** |
| 프런트 킷 `src/meerkit/` | 말모아는 원본 그대로. 매무새는 3개 고침 — 테마 밝게 고정(`theme.ts`·`ThemeSync.tsx`), 내 정보 주소 `/me`→`/mypage`(`config.ts`). **로그인·토큰과 무관** |
| `meerkit.config.ts` | 주석 한 줄(다크 모드 버튼을 끄는 이유)만 다름 — 로그인 잠금·가입·이메일 인증 설정 같음 |
| 킷 템플릿 중 로그인 관련 | 매무새 `main.py`(운영 검사에 매무새 검사 추가)·리프레시 토큰 마이그레이션(앞 리비전 번호만) 수정 — 토큰 동작은 그대로. 말모아는 `main.py` 안 고침(라우터 lifespan) |

그래서 아래 동작은 두 서비스가 같다:

- **액세스 토큰**: JWT(HS256, `JWT_SECRET_KEY`), 30분, 브라우저 메모리에만(`useAuthStore`), `Authorization: Bearer`.
- **리프레시 토큰**: 14일, `meerkit_refresh` 쿠키(httponly·`SameSite=Lax`·경로 `/api/auth`·운영 `Secure`). 서버 DB 에 해시로 기록, **갱신할 때마다 새 토큰으로 회전**, 이미 쓴 토큰이 다시 오면 탈취로 보고 그 로그인(family) 전체 폐기. 로그아웃은 그 기기 family 만 폐기.
- **요청마다 DB 확인** (`load_principal` → `user_from_token`): 탈퇴·정지된 회원, 비밀번호를 바꾸기 전에 발급된 토큰은 바로 거절. 역할은 요청마다 DB 에서 읽으므로 **역할을 빼면 다음 요청부터 바로** 막힌다.
- **프런트 갱신**: 401 이면 킷 `refreshAccessToken()`으로 한 번 갱신 후 다시 보냄. 여러 요청이 동시에 401 이어도 갱신 요청은 하나(single-flight) — 회전하는 리프레시 토큰을 두 번 써서 로그아웃되는 일이 없다.
- 인증번호·비밀번호 재설정 토큰: 킷 `hash_secret`(`JWT_SECRET_KEY`로 HMAC-SHA256)으로만 저장.
- 관리자 역할: `MASTER` 하나 (`ADMIN_ROLE`). 첫 관리자는 `seed-admin.yml`(Actions)로 만든다.

## 2. 다른 것 — 서비스를 쓸 수 있는 사람(권한)

| | 말모아 | 매무새 |
|---|---|---|
| 기준 | **서비스 전체 역할** (킷 역할 표) | **프로젝트별 역할** (매무새 자체 표 `ProjectMember`) |
| 가입하자마자 | 쓸 수 없음 — VIEWER 라 **관리자 승인(OWNER) 대기**, API 403 `MALMOA_NOT_APPROVED`, 화면 "사용 승인 대기" | 바로 씀 — 로그인만 하면 프로젝트를 만들 수 있음 (`require_login`) |
| 통과 조건 | `OWNER` 또는 `MASTER` (`features/malmoa/deps.py` `get_malmoa_user`) | 그 프로젝트 멤버(`project_member`) / 관리자(`project_admin`) (`features/maemusae/access.py`) |
| 남의 데이터 | 모든 작업·일정·참석자가 `user_id`로 나뉘고, **MASTER 도 남의 녹음·회의록을 못 봄** | 멤버가 아니면 404. **MASTER 는 보기만 가능**(고객 지원용, 열람 로그 `project_id`·`actor_id`), 쓰기는 막힘 |
| 사람을 들이는 방법 | 관리자가 회원 관리 창(킷 `AdminMembersPage`)에서 OWNER 부여 | 프로젝트 관리자가 이메일 초대 (아래 3) |
| 킷 함수 | `app.auth.deps.get_current_user` (회원 객체) | `app.core.principal.require_login` (Principal) |

두 킷 함수는 같은 `load_principal` 결과를 읽으므로 검사 강도는 같다 (말모아는 `user.id`가 필요해 회원 객체를 받는다).

**왜 다른가**: 말모아 녹음·원문·회의록은 개인 기록이라 "아무나 가입해서 쓰는" 서비스가 아니다(통합계획 결정 4, 단계 5 결정 A). 매무새는 팀 프로젝트라 프로젝트 단위로 사람을 들인다. 각자 목적에 맞는 선택이라 **맞출 필요 없음**.

## 3. 다른 것 — 서비스가 따로 만든 토큰

| 토큰 | 서비스 | 만들기 | 저장 | 확인 | 무효화 |
|---|---|---|---|---|---|
| Mac 작업자 열쇠 | 말모아 | `scripts/malmoa_worker.py new-token` (`token_urlsafe(32)`) | 서버: `MALMOA_WORKER_TOKEN_HASH`(**SHA-256**, 환경 변수) / Mac: `~/.malmoa-worker.env`(600) | `compare_digest`, `/api/worker/*` 전용 — 회원 토큰으로는 못 씀, 반대도 마찬가지 | 새로 만들어 두 곳을 바꿈 |
| 캘린더 구독 주소 | 말모아 | 회원이 설정 화면에서 (`token_urlsafe(32)`) | DB `malmoa_profiles.ics_token_hash`(**SHA-256**), 주소는 만들 때 한 번만 보여 줌 | 주소 안의 비밀값, 로그인 없음. **요청마다** 탈퇴·정지·승인 취소를 다시 봄(404) | 다시 만들기·끄기 |
| 프로젝트 초대 링크 | 매무새 | 프로젝트 관리자 초대 (킷 `generate_token`) | DB `token_hash`(킷 **`hash_secret` = HMAC**), 원문은 메일에만 | 7일, 한 번만, 행 잠금으로 동시 수락 막음. 초대 이메일 = 로그인 계정 이메일이어야 수락 | 취소·만료·사용 |
| 초대 가입 증표 | 매무새 | 초대 링크로 킷 `issue_verified_email_proof` | 킷 | 킷 가입 API 가 증표 이메일과 가입 이메일 비교 → **인증번호 생략** | 킷 |

**해시 방식 차이 (SHA-256 ↔ 킷 HMAC)**: 말모아 두 토큰은 256비트 무작위 값이라 HMAC 없이 SHA-256 만으로도 DB 가 새어 역산할 수 없다. 그리고 일부러 `JWT_SECRET_KEY`에 묶지 않았다 — 로그인 비밀키를 바꿔도 Mac 작업자·아이폰 구독이 끊기지 않고, 작업자 프로그램은 서버 비밀 없이 해시를 만들 수 있다(트러블 #42). 매무새 초대는 수명이 7일이라 킷 방식을 그대로 쓴 것. **둘 다 맞는 선택, 바꿀 필요 없음.**

## 4. 다른 것 — 개인 AI 키 암호화

| | 말모아 | 매무새 |
|---|---|---|
| 열쇠 | `SECRET_KEY`(임의 문자열) → SHA-256 → Fernet 키 | `MMS_AI_KEY_ENCRYPTION_KEY` = Fernet 키 그대로 |
| 열쇠 바꾸기 | 하나만 — 바꾸면 저장된 키를 모두 다시 넣어야 함 | 쉼표로 여러 개(`MultiFernet`): 새 키를 앞에 넣고 재저장 후 옛 키 삭제 |
| 끄기 | 없음 (화면 설정이 기본) | 스위치 `MMS_USER_AI_KEY_ENABLED` (끄면 서버 키) |
| 운영 검사 | 32자 이상 (`checks.py`) | 켜져 있으면 형식 검사 |
| 로그인 비밀키와 분리 | ✅ (`JWT_SECRET_KEY`와 다른 값) | ✅ |

운영(Render)에는 이 Mac 과 같은 `SECRET_KEY`를 넣었다(6-4) — 데이터를 옮긴 뒤 저장된 AI 키를 그대로 풀기 위해.

## 5. 다른 것 — 화면에서 킷을 쓰는 방식

- **매무새**: 킷 공개 기능(`@/meerkit`의 `api`·`useAuth`·`AuthPanel`·`GuestOnly` 등)으로 화면을 짠다. 깊은 경로는 페이지 부품(`MePage`·`AdminMembersPage`·`LegalPage`·`ResetPasswordPage`)뿐.
- **말모아**: 98 OS 로그인 창·자체 API 클라이언트(`fetch`·업로드 진행률 `XMLHttpRequest`) 때문에 **킷 내부 모듈 9곳을 직접 부른다** — `api/client`(`refreshAccessToken`), `api/error`, `auth/store`(`useAuthStore`), `auth/mutations`(`useLogin`), `auth/lockout`, `auth/dialog-store`, `auth/queries`, `admin/AdminMembersPage`, `legal/content`. 동작은 킷과 같다(같은 갱신 함수·같은 로그인 API·같은 잠금). 가입은 킷 `AuthPanel` 그대로(약관·이메일 인증).
