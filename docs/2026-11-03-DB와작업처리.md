## 바꾼 것

### 5a. DB 설정

- `DATABASE_URL` 기본값(localhost)을 없앴다. 비어 있으면 서버·마이그레이션이 "DATABASE_URL 이 없습니다…"로 멈춘다 (`app/db/session.py`).
- 연결 수 설정 `DB_POOL_SIZE`·`DB_MAX_OVERFLOW` (기본 5·5). 클라우드 DB 는 주소 끝에 `?sslmode=require`, Supabase 는 직접 연결이나 session 풀러를 쓴다 (`.env.example`에 적음).
- 마이그레이션은 이미 앱 밖의 명령(`alembic upgrade head`)이다. 배포에서는 배포 전 단계에서 한 번 돌린다 (6단계).
- 테스트 DB 를 바꿀 수 있게 `TEST_DATABASE_URL` (conftest). 일반 PostgreSQL 16(Docker)에서 전체 테스트를 돌려 확인했다.
- 로컬 개발은 그대로 pgserver.

### 5b. 작업 대기열을 DB 로

예전: 서버 메모리의 `queue.Queue` + "이미 처리 중" 집합. 재시작하면 대기열이 사라지고, 서버가 켜질 때 처리 중이던 작업을 **모두** 실패로 표시했다 (다른 서버가 처리 중인 것까지).

지금 (`services/worker.py`, `core/storage.py`):

| 단계 | 하는 일 |
|---|---|
| 넣기 `enqueue` | API 가 jobs 행에 `task`(transcribe·minutes)와 `queued_at`을 적는다. 이미 대기 중이거나 처리 중이면 거절(409). 행을 잠그고 확인하므로 동시에 눌러도 한 번만 |
| 가져가기 `claim` | 작업자가 `SELECT … FOR UPDATE SKIP LOCKED` 로 가장 오래된 작업 하나를 가져가 `claimed_by`·`heartbeat_at`을 적는다. 서버가 여러 대여도 같은 작업을 둘이 가져가지 않는다 |
| 생존 신호 `heartbeat` | 처리하는 동안 20초마다 `heartbeat_at` 갱신 |
| 끝내기 `release` | 처리 함수가 결과(완료·실패)를 적은 뒤 대기열에서 뺀다. 가져간 작업자만 뺄 수 있다 |
| 복구 `recover_stale` | 생존 신호가 `JOB_STALE_SECONDS`(180초) 넘게 끊긴 작업을 다시 대기열로 (화면: "…중단되어 다시 순서를 기다리는 중"). `JOB_MAX_ATTEMPTS`(3)번 끊기면 실패로 표시 |

- 같은 서버에서 넣은 작업은 바로 가져가고(`wake`), 다른 서버가 넣은 작업은 `WORKER_POLL_SECONDS`(3초)마다 확인한다.
- 역할 `WORKER_TASKS` (기본 `["transcribe","minutes"]`): 배포 서버 `["minutes"]`, Mac 작업자 `["transcribe"]`, `[]`면 작업자 없음.
- 서버가 꺼질 때 처리 중이던 작업은 3분 뒤 다시 대기열로 돌아가 완료 구간부터 이어서 처리한다 (예전처럼 사용자가 다시 누를 필요 없음).
- 서버를 끌 때 작업자를 멈춘다 (`lifespan` 끝에서 `worker.stop()`).
- 응답(`Job`)에는 `task`를 넣지 않는다.
- 마이그레이션 `7680b317a4b3`: jobs 에 `task`·`queued_at`·`claimed_by`·`heartbeat_at`·`attempts`. 예전 메모리 대기열에서 처리 중이던 작업은 이어받을 작업자가 없으므로 예전 재시작 때와 같은 문구로 실패 표시.

### 5c. 회의록 구간 메모를 저장소로

긴 원문을 나눠 정리한 중간 결과를 `work/{id}_minutes/`(서버 디스크) 대신 저장소의 `minutes/{id}.notes/chunk_NNN.json`에 둔다. 무료 서버가 재시작해도 그 구간부터 잇는다. 다 끝나면 지우고, 작업 삭제 범위(`minutes/{id}.`)에 포함된다. 원문을 고치면 버린다 (예전 로컬 위치도 함께 지움).

서버 디스크에 남는 것: 업로드 중 임시 파일(`work/incoming`, 저장소에 올린 뒤 지움)과 저장소에서 잠깐 내려받은 사본(쓰고 지움)뿐이다. 변환 구간 파일(`work/{id}/`)은 변환하는 컴퓨터(Mac 작업자)에만 생긴다.

## 깨우기 (외부 cron)

말모아 저장소에 GitHub 원격이 없어서 GitHub Actions 는 쓰지 않는다. 외부 cron 서비스(예: cron-job.org, 무료·시간대 설정 가능)에 사용자가 직접 등록한다. 가입·등록은 사용자가 한다.

| 항목 | 값 |
|---|---|
| 주소 ① | `https://<말모아 API 주소>/api/health` (DB 확인 포함) |
| 주소 ② | `https://<meerkit API 주소>/health/ready` (DB 확인 포함) — 2026-11-03 추가, 아래 "meerkit 도 깨우기" |
| 방법 | GET, 응답 200 이 아니면 실패로 기록·알림 (503 = DB 문제) |
| 일정 | 월~금, 08:00~19:50, 10분마다 |
| 시간대 | 서비스의 시간대 설정에서 `Asia/Seoul` (팀 시간대가 바뀌면 여기만 고침) |
| 시간 제한 | 90초 이상 (잠든 서버가 깨는 데 약 1분) |

- 한 달 사용 시간 어림: 서버 하나당 평일 12시간 × 약 22일 ≈ 264시간, 두 서버 ≈ 528시간 + 근무 시간 밖 직접 접속분 → 750시간 안. 600시간(80%)을 넘으면 유료 전환 기준 2번으로 다시 판단.

### meerkit 도 깨우기 (2026-11-03 변경)

처음에는 "말모아만 깨우고 meerkit 은 깨우지 않음"으로 정했다가 바꿨다. 이유:
- 액세스 토큰은 30분마다 만료되고, 화면은 만료 뒤 요청이 거절되면 그때 갱신한다 (meerkit `api/client.ts`). meerkit 은 15분 요청이 없으면 잠드므로, 쓰는 도중 **30분마다 약 1분 멈칫**하게 된다.
- 갱신이 실패하면 녹음이 멈추는 문제도 있었다 → 고침 (`06-트러블이슈.md` 29번). 고친 뒤에도 멈칫함은 남으므로 meerkit 도 같은 시간에 깨운다.
- "하루 종일 둘 다 깨우면 모자란다"는 설명이 "근무 시간에도 말모아만"으로 이어졌는데, 근무 시간만이면 둘 다 깨워도 750시간 안이다.

## Mac 작업자 조회 간격 (다음 단계 요구사항으로 기록)

- 평소 1~2분 간격, 서버가 응답하지 않으면 간격을 늘린다 (예: 2 → 4 → 8분, 최대 15분, 응답하면 원래대로).
- **주의 — 사용 시간과 충돌:** Mac 작업자가 밤낮없이 1~2분마다 말모아 API 를 부르면 그것만으로 Render 서버가 잠들지 않아 한 달 내내(약 730시간) 깨어 있게 된다. 평일 08~20시만 깨운다는 결정과 맞지 않고 무료 750시간을 거의 다 쓴다. Mac 작업자 단계에서 둘 중 하나를 정한다:
  - (가) Mac 작업자도 같은 시간대·시간 범위(평일 08~20시) 안에서만 조회한다. 밖에서 올린 변환은 다음 날 아침에 처리.
  - (나) Mac 작업자가 API 가 아니라 DB 대기열(Supabase)을 직접 본다. 서버를 깨우지 않지만 Mac 에 DB 접속 정보가 있어야 한다.
